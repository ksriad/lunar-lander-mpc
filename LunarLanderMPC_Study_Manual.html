1Executive Summary & Project Objectives

This is a single MATLAB App — LunarLanderMPC.m — that simulates a rocket-powered lander descending onto the Moon in a 2-D vertical plane (altitude vs. horizontal position, plus pitch). It can be flown two ways: manually, using the keyboard, or autonomously, using a hand-built Model Predictive Controller (MPC) with a dedicated terminal-guidance law for the final touchdown. Everything — the physics, the controller, the numerical methods, and the landing-safety logic — is written from scratch in plain MATLAB, deliberately avoiding MATLAB's built-in black-box equivalents (no backslash/inv() for the MPC solve, no polyfit, no interp1, no trapz/integral, no fzero) so that each underlying numerical method is genuinely demonstrated, not just invoked.

Beginner-friendly summary
Think of it like the classic arcade game Lunar Lander, but built as a real engineering simulation: gravity constantly pulls the ship down, a rocket engine can be throttled to fight gravity and slow the descent, and small side-thrusters (RCS) can tip the ship to steer it sideways. A landing only counts as "safe" if all three legs touch the ground at (almost) the same instant, upright, and slowly. You can fly it yourself with the arrow keys, or let an autonomous "co-pilot" (the MPC controller) fly it for you.

What problem does the project solve?

Landing softly on an airless world is a genuinely hard control problem: gravity never stops pulling, fuel is finite, and the vehicle only has two independent control knobs (thrust magnitude and one torque) to satisfy several simultaneous, tight requirements at touchdown — low sideways speed, low descent speed, near-zero tilt, near-zero spin, and all three landing legs on the pad together. This project builds a small but complete closed-loop system that solves exactly that problem, end to end: physics → sensing (perfect, simulated) → control decision → actuation → physics again, 25 times a second.

Why does autonomous landing need feedback control at all?

A rocket sitting 120 m above a pad, 60 m off to one side, cannot simply be told "go there" — the only way to move sideways in this model is to tilt, which also changes how much lift the same thrust produces vertically. Every command interacts with every other state. An open-loop plan (compute a trajectory once, in advance, and blindly execute it) would be knocked off course by the smallest modeling error or disturbance and could easily overshoot the pad, run low on fuel, or slam into the ground. Feedback control continuously re-measures the actual state and re-computes the control action, so errors get corrected instead of accumulating.

Why is MPC an appropriate choice here?

Model Predictive Control doesn't just react to the instantaneous error like a simple feedback law — it uses a model of the vehicle to explicitly predict several seconds ahead and chooses the whole future control sequence that minimizes a cost function (tracking error + control effort + smoothness) before applying only the very first action and re-planning next tick. That's a natural fit for landing, where the "right" thing to do right now (e.g. how hard to brake) genuinely depends on what's coming up (how much altitude and fuel margin is left).

Manual vs. Autonomous mode

Manual / Interactive Pilot

The human directly commands thrust (ramped by holding UP/DOWN) and torque (bang-bang via LEFT/RIGHT). There is no predictive planning — the pilot is the "controller," reacting to the live telemetry and keyboard diagnostics panel.

Autonomous MPC

Every 0.04 s, a target state is computed from the current altitude/distance to the pad, the MPC solves a fresh optimization problem for the best control, and (below 45 m altitude) a dedicated terminal-guidance law takes over to nail the final touchdown tolerances.

Main objectives

  • Simulate believable, numerically well-behaved 2-D rocket dynamics with fuel consumption and actuator limits.
  • Provide responsive manual flight control via the keyboard, decoupled from the fixed-rate physics loop.
  • Design and implement a real MPC controller (linearization, discretization, prediction, cost function, constrained solve) that can fly the vehicle to a safe landing autonomously.
  • Implement and validate a suite of classical numerical methods (interpolation, regression, linear-system solving, differentiation, integration, root-finding) and use the genuinely useful ones in a real post-flight analysis pipeline.
  • Detect landing success/failure using a physically meaningful, geometrically precise three-leg contact model.

Expected outputs / educational purpose

The primary output is the live, animated simulation itself plus a post-flight analysis window with four response plots (position, acceleration, attitude, thrust) and a numeric summary. Educationally, the project is a vehicle for demonstrating — in one coherent, motivating context — ordinary differential equations and numerical integration, linear algebra and linearization, constrained optimization concepts, and classical numerical-methods coursework (EEE 212 Experiments 3–8), rather than teaching each in isolation.

Engineering significance & practical applications

The core techniques — linearize-discretize-predict-optimize MPC, receding-horizon control, gain-scheduled terminal guidance, and rigorous multi-condition safety classification — are the same conceptual building blocks used in real spacecraft guidance, reusable-rocket landing, and precision robotic descent, even though this project's specific model is deliberately simplified (see Limitations). It is explicitly not presented as flight-ready or physically exhaustive — see Technical Honesty.

File → Function → Function → Variable → Output map

At the top level, four independent modules (matching the project's four-person team structure, visible in file headers throughout) are wired together by the GUI class:

physics/ (Person 1)

Owns the equations of motion, integration, fuel/mass model, actuator saturation, and the three-foot touchdown geometry test. Public entry point: simulateStep.m.

mpc/ (Person 2)

Owns linearization, discretization, prediction-matrix construction, the quadratic cost function, the hand-coded Gauss-Jordan solver, and actuator-constraint enforcement. Public entry point: mpcController.m.

numerical/ + analysis/ (Person 3)

Owns the EEE212 numerical-methods toolbox (interpolation, regression, differentiation, integration, root-finding) and the post-flight telemetry analysis pipeline. Public entry points: analyzeFlight.m, individual numerical functions.

LunarLanderMPC.m (Person 4)

Owns the GUI, the keyboard architecture, the fixed-rate simulation timer, mode switching, terminal-guidance override, drawing, and landing/crash state transitions. This is the only file that calls into all three other modules.

Two modules exist in the ZIP but are not reachable from the live app
terrain/generateTerrain.m (which itself calls numerical/lagrangeInterpolation.m) and analysis/prepareResponseData.m are both fully implemented, documented, and exercised by the test suite — but a project-wide search confirms neither is ever called from LunarLanderMPC.m. The live GUI draws its own hand-crafted decorative terrain directly inside drawStaticScene, and builds its four analysis plots directly from telemetry inside showAnalysisWindow rather than calling prepareResponseData first. MPC tuning parameter (cost function)		diag([30 220 60 260 180 35])mixed (state-tracking weights)physics/initializeLander.m; mpcController.m

Why needed: Without state weights, the optimizer would have no notion of which errors matter more — e.g. attitude error should be punished more than a small velocity error near hover.
Why this value: Entries were tuned by the project's designer: y (index 3, weight 60) and vy (index 4, weight 260) are weighted heavily because vertical descent-rate control is safety critical; theta (weight 180) is also heavily weighted to keep the vehicle upright; x (30) and vx (220) get intermediate/heavy weight to converge laterally onto the pad; omega (35) is weighted least of the six.

↓ That state is allowed to drift further from target before the optimizer 'cares'.

↓ Optimizer chases tracking error more aggressively, possibly with larger/noisier control commands.

Terminal-guidance tuning (PD gain schedule)		7 altitude bands, 45→30→20→12→8→5→2.5mmixedLunarLanderMPC.m (applyTerminalLandingGuidance)

Why needed: A single fixed gain would either be too gentle far from the ground (slow convergence) or too aggressive near the ground (overshoot/oscillation risking a tilted or off-pad landing); gain scheduling lets the controller be assertive early and delicate at the very end.
Why this value: KpX rises from 0.22 to 0.95 and KdX from 1.65 to 3.20 while aMax (the ceiling on commanded lateral acceleration) shrinks from 2.40 to 0.35 m/s² as altitude drops from 30m to under 2.5m — i.e. the controller reacts increasingly strongly to a GIVEN error, but is allowed a shrinking maximum authority, biasing it toward small, precise corrections rather than large last-second maneuvers.

Numerical safeguard		1e-10·scale / 1e-8·scale / 1e-9·scalesame units as Hmpc/gaussJordanSolve.m

A subtlety worth knowing: rendering rotation vs. dynamics sign convention
The rotation matrix used everywhere in drawDynamicScene to draw the rotated body/nose/legs is the standard counter-clockwise rotation matrix R = [[cosθ, −sinθ], [sinθ, cosθ]]. Applying it to the local “nose-up” direction (0,1) gives a world direction of (−sinθ, cosθ) — i.e. for a small positive θ, the drawn nose leans slightly toward −x (left). But the dynamics equations (ax=(T/m)sinθ) say a positive θ accelerates the vehicle toward +x (right) — consistent with a thrust unit vector of (sinθ, cosθ), which is the opposite horizontal sign from what the drawing's rotation matrix would produce if you rotated the local “up” vector by the same +θ. Both pieces of code are internally self-consistent (rendering is consistent with itself; dynamics is consistent with itself), and this does not affect the correctness of the closed-loop control — the MPC and terminal guidance are tuned directly against the landerDynamics.m equations, not against the picture. But if a strict examiner asks you to visually confirm “does the nose tip toward the direction the ship accelerates,” the honest, defensible answer is that this specific detail was identified by reading the two pieces of code algebraically side-by-side, not by confirming it visually in a running MATLAB session (no MATLAB runtime was available while preparing this documentation). It's exactly the kind of fine-grained consistency question a strict examiner might probe — know the derivation, not just the conclusion.

Beginner → Intermediate → Advanced: the dynamics

BASIC

Gravity pulls the ship down. The rocket engine pushes it up (and, if tilted, sideways too). Little side-thrusters can tip the ship left or right.

INTERMEDIATE

Six numbers (position, velocity, attitude, spin) fully describe the ship at any instant. Newton's second law (F=ma) turns the thrust and torque into accelerations; because thrust is body-fixed, tilting the ship is the ONLY way to steer sideways.

ADVANCED

This is a control-affine nonlinear system: state_dot = f(state) + g(state)·control, where the nonlinearity is entirely the sin/cos of theta multiplying thrust. The MPC linearizes this exactly at the hover point (θ=0) where sinθ≈θ≈0 and cosθ≈1, which is why position doesn't appear in the linear A/B matrices at all (translation invariance).

Why lunar gravity differs from Earth's, and why that matters here

The Moon's gravity (1.62 m/s²) is about 1/6 of Earth's (9.81 m/s²) because the Moon has much less mass and a smaller radius. This is a real physical constant, not a tunable design choice — unlike almost every other numeric constant in this project, changing it would mean simulating a different world (e.g. 3.71 m/s² for Mars), not "re-tuning" the Moon scenario.

How gravity interacts with thrust and the MPC

Because gravity is constant and unavoidable, the vehicle must always produce at least T=m·g of vertical thrust just to hover — this is exactly the MPC's linearization operating point (u0=[m·g;0] in linearizeLander.m), meaning the whole MPC solves for a control increment away from "just enough thrust to counteract gravity," not from zero. If g were increased, every one of the MPC's predicted trajectories, the terminal guidance's thrust law, and the required tilt angle for a given lateral maneuver would all shift accordingly — but because everything reads params.g consistently, changing it once in initializeLander.m would correctly re-parametrize the entire simulator.

10Thrust Model

Thrust is a single scalar magnitude T ≥ 0 (the engine can only push, never pull) whose direction is entirely determined by the current attitude θ — there is no independently steerable thrust vector, and no separate horizontal thruster.

Fx = T·sin(θ)     Fy = T·cos(θ)
ax = Fx/m     ay = Fy/m − g

The sin/cos terms exist because thrust is a body-fixed force: at θ=0 all of it goes into Fy (straight up); as the vehicle tilts, thrust is geometrically decomposed into a horizontal and vertical world-frame component, exactly like resolving a force vector along rotated axes.

Throttle / continuity

Thrust is continuously variable (not discretely staged) between 0 and Tmax=15000 N. In Manual mode it is only ever changed by a fixed ramp rate (ManualThrustRate=1800 N/s) while UP/DOWN is held — a proportional-feeling throttle built from a binary key signal. In Autonomous mode, the MPC (or, below 45m, the terminal guidance law) can request any value in [0,Tmax] directly, with no ramp limit of its own (though the underlying physical dynamics obviously still respond continuously).

Saturation & fuel-limiting (the actual order of operations, from simulateStep.m)

  1. Commanded T is clamped to [0, Tmax]; commanded tauRCS is clamped to [-tauMax, tauMax].
  2. Fuel-limited thrust: since dm_fuel/dt = -T/ve integrates EXACTLY (for constant T over one step) to fuelBurn = (T/ve)·dt, the largest thrust the remaining fuel can sustain for one full step is computed in closed form: maxThrustFromFuel = fuelMass·ve/dt, and T is further reduced to this value if necessary — not integrated first and clamped afterward.
  3. After integration, θ is clamped to [-thetaMax, thetaMax] as a last-resort physical safety net (see Error Handling & Safety).
Why this order matters
Computing the fuel-limited thrust BEFORE integrating (rather than integrating with the full commanded thrust and clamping fuel to zero afterward) means the acceleration actually used in the dynamics, and the thrust value reported in telemetry, are always the thrust that was truly deliverable — never silently wrong by ignoring a fuel shortfall.

The fuel-burn ODE, solved in closed form

dm_fuel/dt = −T / ve

Because T is held constant (zero-order hold) across one dt, this linear ODE integrates exactly, with no numerical scheme needed:

ΔfuelMass = (T/ve)·dt     newFuelMass = max(0, fuelMass − ΔfuelMass)     newMass = dryMass + newFuelMass

This is deliberately NOT run through Euler/RK2 alongside the other 6 states — there's no benefit to approximating an ODE that has an exact solution, and doing it in closed form makes "fuel never goes negative" trivial to guarantee up front (see the Thrust Model section's fuel-limiting step) rather than clamped after the fact.

What happens when fuel is exhausted

Once fuelMass≤0, simulateStep forces T_eff=0 regardless of what was commanded — the vehicle becomes a pure ballistic (gravity-only) projectile from that point on. In Manual mode, getManualControl independently double-checks this and also forces T=0, so there are two layers guaranteeing thrust cannot exceed available fuel.

Does the MPC account for changing mass?

Yes, explicitly and every single call: mpcController re-reads params.mass (the CURRENT mass, post-fuel-burn) and calls linearizeLander fresh with it every tick — the linear model used for prediction is always built around the vehicle's actual current mass, not a stale or initial value.

Simplification called out explicitly

Mass is held constant during the integration of one step (zero-order hold), then updated afterward for the next step. At dt=0.04s and the default thrust range, one step burns roughly 0.002% of the vehicle's mass — an explicitly documented, negligible approximation, not a physics compromise.

13Autonomous / MPC Mode

Beginner level: what is feedback control?

A feedback controller continuously measures the system's actual state and compares it to a desired target, using the difference (the error) to decide what to do next — as opposed to a fixed, pre-computed plan that ignores what's actually happening. Feedback is what lets a controller correct for surprises (wind, a heavier-than- expected vehicle, a slightly wrong model) instead of blindly executing a script.

Beginner level: what is Model Predictive Control?

MPC is a feedback strategy that, instead of reacting only to the CURRENT error, uses a model of the system to simulate several steps into the future for many possible action sequences, picks the sequence that best satisfies a cost function (get close to the target, don't use too much control effort, don't be jerky), but only actually does the very first action of that plan. Next time step, it senses the new actual state and repeats the whole prediction+optimization from scratch. This "plan ahead, but only commit to the first step, then re-plan" idea is called the receding horizon principle.

Why is MPC useful for a lunar lander specifically?

Landing has hard, simultaneous, competing objectives (get to the pad, don't run out of fuel, don't hit the ground too fast, stay upright) and a well-understood dynamic model (Newton's laws). MPC's cost function naturally expresses "care about all of these together, with these relative priorities," and its predictive nature lets it start braking early rather than reacting only once a problem (e.g. excessive descent speed) is already occurring.

The actual implementation, end to end

Two cooperating pieces run every control tick (0.04 s) while in Autonomous mode:

  1. makeMPCTarget (in LunarLanderMPC.m) looks at the current altitude and distance to the pad and produces a target state — not just a fixed final position, but an altitude-scheduled target velocity too (fast descent far up, slow near the ground; capped lateral speed as altitude drops).
  2. mpcController (in mpc/) takes that target plus the current state and params, and returns the optimal [T;tauRCS] for THIS tick only, plus a predicted trajectory for the dashed overlay line shown on screen.
  3. applyTerminalLandingGuidance then either passes that control through unchanged (above 45m foot-altitude) or completely overrides it with a separate, hand-tuned PD control law (below 45m).

Prediction model, horizon, cost function, constraints (overview — full detail in the next sections)

  • Prediction model: a LINEARIZATION of the true nonlinear dynamics about hover, discretized to x(k+1)=Ad·x(k)+Bd·Δu(k).
  • Prediction horizon Np=70 steps (2.8 s); control horizon Nc=12 steps.
  • Cost function: quadratic tracking (Q) + control-effort (R) + control-smoothness (S) terms.
  • Constraints: actuator saturation is a true HARD constraint; attitude bounds are only a SOFT, diagnostic-only post-hoc correction (explicitly documented as such — see Constraints).
  • Optimization: the cost function's minimum is found analytically by solving a linear system of normal equations (an unconstrained least-squares QP) via hand-coded Gauss-Jordan elimination — NOT an iterative optimizer like fmincon/quadprog.
  • Receding horizon: only the first of the 12 optimized control moves is ever applied; the whole problem is rebuilt and re-solved from scratch next tick.
  • Control update frequency: every 0.04 s (25 Hz), same as the physics tick.
  • Saturation: hard-clamped to [0,Tmax] and [-tauMax,tauMax] inside applyMPCConstraints.
  • Safety logic: a soft, diagnostic-only attitude check (does NOT re-solve the QP).
  • Landing/final descent logic: handled by the SEPARATE applyTerminalLandingGuidance law below 45m, not by the general MPC.
  • Mode switching: a single altitude threshold (45m foot-altitude) switches between "raw MPC" and "terminal guidance override," recomputed fresh every tick (not a persistent state machine flag).

Linearization: A, B matrices

The nonlinear dynamics are linearized about the hover operating point (θ₀=0, ω₀=0, T₀=m·g, tau₀=0), by hand-derived Jacobian entries (not MATLAB's symbolic/numeric Jacobian tools):

A (6×6): A(1,2)=1  (dx/dt=vx)    A(2,5)=g  (dvx/dt sensitivity to θ at hover, since T₀/m=g)
         A(3,4)=1  (dy/dt=vy)    A(5,6)=1  (dθ/dt=ω)    all other entries = 0

B (6×2): B(4,1)=1/m  (dvy/dt sensitivity to thrust deviation)    B(6,2)=1/I  (dω/dt sensitivity to torque)    all other entries = 0

u₀ = [m·g ; 0]

Columns 1 and 3 of A (the x and y position states) are exactly zero — this is translation invariance: the hover equilibrium condition f(x_eq,u0)=0 holds for ANY position, so position never needs to appear in the linear model, and no affine/offset correction term is required. The model can be written directly as x_dot = A·x + B·Δu using the ABSOLUTE state x and the control increment Δu = u − u₀.

Discretization: Ad, Bd

Ad = I + A·dt     Bd = B·dt

This is a first-order (explicit-Euler-style) approximation of the exact zero-order-hold discretization (Ad_exact = expm(A·dt)), chosen because dt=0.04s is small relative to the vehicle's time constants, and computing a matrix exponential every 0.04s would be unnecessary extra cost for negligible extra accuracy at this horizon.

Prediction matrices: F, Φ

The entire predicted trajectory is expressed as one linear map from the current state and the future control increments:

X = F·x0 + Φ·ΔU
MatrixDimensionsMeaning
F(n·Np)×n = 420×6Maps the current state to the free (zero-control-increment) response over the whole horizon

Building the QP: H, rhs

H = Φ'·Q̄·Φ + R̄ + D'·S̄·D     (24×24)
rhs = −Φ'·Q̄·f₀     (24×1),   where f₀=F·x0−x_ref,stacked

where Q̄=kron(I_Np,Q), R̄=kron(I_Nc,R), S̄=kron(I_Nc,S), and D is the control-increment difference operator (D·ΔU stacks Δu(j)−Δu(j−1), with Δu(−1):=0 since the controller is stateless between calls). H is symmetrized (H=(H+H′)/2) to remove floating-point asymmetry before solving.

Solving: gaussJordanSolve (Experiment 5)

H·ΔU = rhs is solved via hand-coded Gauss-Jordan elimination with partial pivoting — explicitly NOT MATLAB's \ or inv(). At each column, the largest-magnitude available candidate (at or below the diagonal) is chosen as the pivot and swapped into place; if even the best candidate falls below a Frobenius-norm-scaled tolerance, a tiny ridge term is added to rescue it (info.regularized=true); if it's still effectively zero, the solve is flagged info.singular=true rather than crashing. info.residual = norm(H·x−rhs) is always computed so solve quality is visible even on a degraded solve.

Reconstructing the applied control

deltaU1 = ΔU(1:2)     uNominal = u₀ + deltaU1     control = applyMPCConstraints(uNominal, ...)

Only the FIRST control move (2 of the 24 solved numbers) is ever reconstructed into an absolute [T;tauRCS] and returned — the receding-horizon principle in code.

15Cost Function

J = Σi=1..Np (x(k+i)−x_ref)′Q(x(k+i)−x_ref)  tracking
  + Σj=0..Nc-1 Δu(j)′RΔu(j)  control effort
  + Σj=0..Nc-1 (Δu(j)−Δu(j-1))′S(Δu(j)−Δu(j-1))  control smoothness, Δu(-1):=0

This matches the ACTUAL implementation in buildCostMatrices.m exactly — there is no generic textbook MPC formula substituted in its place.

Why three separate terms?

Tracking (Q)

Without this, the controller would have no reason to go anywhere near the target at all — this is the term that actually drives the vehicle toward the pad.

Control effort (R)

Without this, the unconstrained least-squares optimum could demand extreme/oscillatory thrust or torque even when a gentler command achieves nearly the same tracking — this term discourages "wasteful" control magnitude.

Smoothness (S)

Without this, consecutive optimized control moves could jump around erratically even if each individually seems reasonable — this term discourages jerky control sequences.

What happens if Q increases?

Tracking error is punished more heavily relative to R/S, so the optimizer accepts more control effort/less smoothness to reduce it — the controller becomes more aggressive about closing the gap to the target. This is exactly what the code's own terminalFactor logic does on purpose: Q's x/vx/theta/omega entries (indices 1,2,5,6) are multiplied by 1.8×–3.5× as altitude drops below 35/15/8m, deliberately sharpening the controller's focus on centering and leveling out as touchdown approaches.

What happens if R increases?

The optimizer becomes more conservative about control magnitude, potentially trading away some tracking accuracy to avoid large commands — predicted trajectories become gentler/lazier. Since R is deliberately kept very small relative to Q (0.015–0.04 vs. up to 260), tracking dominates the shipped tuning by design.

Diagnostic use of J

mpcController reports the resulting cost as info.cost, but the code never checks this value against a threshold or re-solves if it's "too high" — it's purely a diagnostic number a caller (e.g. the GUI) COULD display, not something the algorithm itself acts on.

16Constraints

This is one of the most important, and most carefully-documented, design points in the whole MPC engine: the project draws a hard line between what IS and is NOT a genuine hard constraint.

Hard constraints (guaranteed)

  • 0 ≤ T ≤ Tmax (15000 N)
  • |tauRCS| ≤ tauMax (500 N·m)

Enforced by simple clamping in applyMPCConstraints.m AND, independently, again in simulateStep.m — the value ACTUALLY applied to the real physics can never violate these, no matter what the QP solved for.

Soft / not guaranteed

  • |θ| ≤ thetaMax (0.5236 rad) over the PREDICTED horizon

The core QP (an unconstrained least-squares solve) has NO knowledge of thetaMax at all. If the unconstrained prediction's max |θ| exceeds it, applyMPCConstraints only records this as a diagnostic (thetaPredicted) — the code explicitly does NOT re-solve the QP or scale tauRCS based on it (an earlier, rejected idea, with the reasoning left in the code's own comments: scaling based on a distant, unreliable long-horizon prediction could dangerously reduce a NECESSARY braking torque down to almost nothing). The physics engine's own hard theta clamp (in simulateStep) and the terminal-guidance law are what actually keep attitude in check in practice.

Why not solve a truly constrained QP?

A genuine hard-state-constrained optimization would require constrained solvers (active-set, interior-point, etc.), which the project's own real-time-solver requirement explicitly disallows in favor of the fast, direct Gauss-Jordan linear solve demonstrated here. This is a deliberate, documented trade-off: simplicity and real-time speed vs. formally guaranteed constraint satisfaction.

17Landing &amp; Crash Detection

Landing/crash detection is the single decision point checkLandingStatus, called every tick from checkTermination and once more (on the final sample) from calculateFlightMetrics.

checkLandingStatus(state, params) | |-- tumbling = abs(theta) > pi/2 ? -----> YES: status='crash' (tumbling), STOP |-- outOfBounds = abs(x)>135 OR y<target.y-20 ? -> YES: status='crash' (out of bounds), STOP | '-- otherwise: contact = getLandingContact(state, params) | |-- contact.contactDetected == false ? --> status='flying' (still airborne) | '-- contact.contactDetected == true: | |-- contact.safeTouchdown == true --> status='safe' (LANDED) '-- contact.safeTouchdown == false --> status='hard' (CRASH / hard landing)

What must be true for "LANDED"?

contact.safeTouchdown requires ALL of the following simultaneously (a logical AND of every single condition below):

Geometric conditions (contact.simultaneous)

  • allFeetInside: every foot's x-position within the pad's usable half-width (7−0.75=6.25m of the pad center)
  • allFeetTouching: every foot within footPenetrationTol=0.02m of the pad surface
  • balanced: the spread between the highest and lowest foot ≤ footHeightTol=0.03m

Kinematic conditions (contact.safeKinematics)

  • |vx| ≤ 0.20 m/s
  • |vy| ≤ 0.60 m/s
  • |θ| ≤ 0.005 rad (≈0.29°)
  • |ω| ≤ 0.08 rad/s
What makes it say &ldquo;CRASHED&rdquo;?
Three independent paths, ANY one of which is sufficient: (1) tumbling (|θ|>90°), (2) flying out of the world bounds (|x|>135m or too far below the pad), or (3) touching the ground WITHOUT satisfying every single geometric + kinematic condition above (a 'hard' landing). Note that tumbling/out-of-bounds are checked FIRST and unconditionally — a tumbling vehicle is a crash even if it happens to also be near the pad.

Why require all three feet, not just detecting any contact?

A single foot touching down first (while the other two are still above the pad) means the vehicle is not actually resting stably on three support points — physically, it would likely tip. The balanced check (feet within 3cm of each other in height) combined with allFeetTouching is how the code verifies "all three simultaneously," without simulating any actual post-contact tipping dynamics.

What happens physically once a safe touchdown is detected?

Inside simulateStep's enforceLandingPadCollision local helper: if contact.safeTouchdown is true, the state is snapped to a clean rest position (feet exactly on the pad, velocities and omega zeroed, theta held) rather than left at whatever slightly-penetrating or slightly-off values the raw integration produced — giving a visually clean, physically sensible "settled" final frame. If contact is detected but NOT safe, the state is left as integrated (the crash is simply reported, not artificially corrected).

18Landing Pad / Terrain Geometry

Visual geometry and physics/collision geometry are ENTIRELY separate in this project

  • Usable half-width for a foot's CENTER: 7 − footPadHalfWidth(0.75) = 6.25 m (accounts for the foot's own physical extent, not just its centerline)

20Simulation Loop

This is the ACTUAL sequence executed once per timer tick, reconstructed directly from timerCallback:

timerCallback(app) [fires every dt=0.04s] 1. preStatus = checkLandingStatus(app.State, app.Params) if preStatus != 'flying': checkTermination(app); return (resolves a vehicle that already touched down on the PREVIOUS tick, before asking for a brand-new control command) 2. if app.Mode == 'Manual': control = getManualControl(app) else: (Autonomous) target = makeMPCTarget(app) [mpcControl, prediction, info] = mpcController(app.State, target, app.Params) control = applyTerminalLandingGuidance(app, app.State, mpcControl, app.Params) app.Prediction = prediction (drives the dashed predicted-path overlay) 3. [stateNext, paramsNext, telemetry] = simulateStep(app.State, control, app.Params) 4. app.State = stateNext ; app.Params = paramsNext ; app.Control = control app.FlightTime = app.FlightTime + app.Params.dt 5. logTelemetry(app, telemetry) (append one sample) 6. drawDynamicScene(app) (redraw lander body/legs/trail) 7. updateTelemetryLabels(app) (refresh the 8 text labels) 8. updateKeyboardDiagnostics(app) (refresh T/tauRCS readouts) 9. checkTermination(app) (checkLandingStatus on the NEW state; stop timer + set status if no longer flying) 10. drawnow limitrate (yield to the graphics renderer, skip if busy)
Why check termination at the TOP of the callback too?
Step 1's pre-check exists because the timer could fire once more after the vehicle already landed/crashed on the previous tick (a scheduling race in any timer-driven loop); resolving this FIRST, before computing a brand-new control command for an already-finished flight, keeps the app from momentarily computing and applying a nonsense control to a vehicle that should already be stationary.

22Visualization

Drawing is split into a one-time STATIC pass and a per-frame DYNAMIC pass — a standard, important MATLAB graphics-performance idiom.

drawStaticScene (once, at start/reset)

  • Starfield (fixed random seed rng(12), 80 stars — reproducible every run)
  • Decorative moon backdrop and craters
  • Decorative hand-crafted cratered ground (sine + Gaussian, NOT physics-relevant)
  • Landing pad graphics (the physics-relevant flat segment, drawn as a highlighted platform)
  • Creates every graphics HANDLE that drawDynamicScene will later update (initialized blank/NaN)

drawDynamicScene (every tick)

  • Rebuilds the local-frame body/nose/stripe/leg/foot shapes
  • Rotates all of them by the SAME rotation matrix R=[[cosθ,-sinθ],[sinθ,cosθ]]
  • Translates by the current (x,y)
  • Updates ONLY the .XData/.YData of the existing handles (never re-creates graphics objects)
  • Appends to and redraws the flight TrailLine
Why update .XData/.YData instead of re-plotting?
Creating a new graphics object every frame (e.g. calling plot() again 25 times a second) is significantly slower than mutating an existing handle's data properties, and can also leak graphics objects if old ones aren't explicitly deleted. This project creates every shape ONCE in drawStaticScene/at first draw, then only ever updates coordinates afterward — plus calls drawnow limitrate instead of plain drawnow, letting MATLAB skip a redraw if the previous one hasn't finished rendering yet.

A real bug the test suite caught (worth telling this story in viva)

An early draft of richardsonDerivative.m used the Romberg-style combination (16·D(h/2) − D(h)) / 15, which is only mathematically valid when combining two estimates that are ALREADY 4th-order accurate. Since a plain central difference is only 2nd-order (O(h²)) accurate, the correct Richardson combination is (4·D(h/2) − D(h)) / 3. This was caught by comparing against the known derivative of a test function in testNumericalMethods.m, and is explicitly documented as a caught-and-fixed mistake in documentation/NUMERICAL_METHODS.md.

34One Complete Flight Walkthrough (Autonomous)

A narrative reconstruction of one full autonomous flight, phase by phase, tied to the actual functions/variables that execute during each phase.

Phase 1 — Initialization

startupFcn calls initializeLander(), which returns state0=[-60;4;120;-1.2;0.08;0] (60m left of the pad, moving right at 4 m/s, 120m up, descending at 1.2 m/s, tilted 4.6°) and the full params0 struct. The scene is drawn, telemetry initialized, and the status shows READY. Pressing Start seeds telemetry sample 1 and starts the 25Hz timer.

Phase 2 — Initial descent (altitude > 45m)

Every tick: makeMPCTarget reads the current altitude and sets a fast descent-rate target (desiredVy as negative as −7 m/s while above 50m, per the altitude schedule) and a lateral-approach velocity target (via the aBrake-based kinematic formula, capped by altitude). The raw mpcController output is applied directly (altitude > 45m, so applyTerminalLandingGuidance passes it through unchanged). The vehicle tilts to correct its 60m lateral offset, burning fuel and losing altitude.

Phase 3 — Horizontal correction

As |x| shrinks, makeMPCTarget's desiredVx shrinks correspondingly (the aBrake kinematic formula naturally produces a decelerating profile), and the required tilt angle drops. Q's heavy weighting on vx (220) and theta (180) keeps this correction assertive but not wild.

Phase 4 — Approach to the landing zone (altitude crossing 45m)

The instant foot-altitude drops to or below 45m, applyTerminalLandingGuidance begins fully overriding the MPC's output. The altitude-scheduled KpX/KdX/aMax ladder takes over lateral control, and the desiredVy ladder (from −2.2 down toward −0.30 m/s as altitude drops through 15/8/4m) takes over vertical control. The MPC's own mpcController call still runs every tick (its output is simply discarded below 45m) — a slightly wasteful but harmless design choice.

Phase 5 — Final descent (altitude < 12m, then < 5m)

The anti-drift holdback gates activate: if vx, |θ|, or |ω| are still above their settling thresholds, the controller raises its own minimum vy (refusing to descend as fast as the nominal schedule would allow) — actively buying time for the vehicle to settle before continuing down. thetaCommand is simultaneously squeezed toward zero by the shrinking braking-angle scale factor, so any remaining lateral-correction tilt is being actively removed during this same window.

Phase 6 — Touchdown

Once the lowest foot's y comes within footPenetrationTol=0.02m of the pad, getLandingContact (called from inside simulateStep's enforceLandingPadCollision) evaluates every geometric and kinematic condition simultaneously. If all pass, the state is snapped to a clean rest position.

Phase 7 — Landing validation

checkTermination calls checkLandingStatus on the new (post-contact) state; getLandingContact is re-evaluated and, if safeTouchdown is true, the timer is stopped and StatusLabel turns green with "LANDED." If any single condition failed (e.g. vy still 0.7 m/s), the label turns red with "CRASH / HARD LANDING" instead — the exact same code path structurally, just a different branch of the same classifier.

The same walkthrough, conceptually, for Manual mode

Phases 1–2 are identical (initialization, then a human-controlled descent instead of MPC-controlled). There is no Phase-4-style automatic handover to terminal guidance in Manual mode — the human pilot is responsible for the ENTIRE approach and final descent, using only the ramped-thrust/bang-bang-torque controls and the live telemetry/keyboard-diagnostics panel as feedback. Phases 6–7 (touchdown, validation) run through the exact same getLandingContact/checkLandingStatus logic regardless of which mode flew the approach — landing success is judged identically either way.

BASICWhat is thrust, physically, and how does it produce acceleration?
Viva answer: Thrust T is the force (in Newtons) the main engine exerts on the vehicle; by Newton's second law, acceleration = force/mass, so it enters the dynamics divided by mass: ax=(T/m)sinθ, ay=(T/m)cosθ−g.

Because thrust direction is tied to attitude (theta) rather than being independently steerable, EVERY horizontal maneuver in this simulator is secretly an attitude maneuver — there is no separate side-thruster for translation.

BASICWhy does mass matter, and why does it change during flight?
Viva answer: Mass sets how much acceleration a given thrust produces (a=F/m); it decreases over time because burning fuel consumes propellant mass (dm/dt=−T/ve), so the SAME commanded thrust produces slightly more acceleration late in the flight than early on.

This is why the MPC re-linearizes (calls linearizeLander/discretizeModel) EVERY single call, using the current params.mass — the linear model used for prediction is only valid at the instant it's built.

INTERMEDIATEWhat's the difference between weight and thrust-to-weight ratio here, and why does it matter?
Viva answer: Thrust-to-weight ratio (Tmax / (mass·g)) determines whether the vehicle CAN hover/decelerate at all; here at initial mass 2000kg, Tmax/(2000·1.62) ≈ 4.6, meaning nearly 5× more thrust is available than needed just to hover.

BASICWhy is there no atmospheric drag term in the dynamics?
Viva answer: The Moon has no meaningful atmosphere, so a real lunar descent genuinely experiences no aerodynamic drag — omitting it here is physically correct, not a simplification.

E · MPC questions

BASICWhat is MPC, in one sentence?
Viva answer: A control method that, every control step, uses a model to predict several future steps ahead, chooses the sequence of actions that minimizes a cost function over that horizon, but only actually applies the FIRST action — then repeats the whole process next step with updated information (receding horizon).

Contrast with a simple feedback law (like PID) which reacts only to the instantaneous error; MPC explicitly plans ahead using a model, which is why it needs A/B matrices and a prediction horizon Np at all.

INTERMEDIATEWhy is MPC appropriate for a lunar lander?
Viva answer: Landing has hard, simultaneous constraints (fuel is finite, thrust is bounded, the touchdown must be slow/level/centered) and a clear, model-known dynamics (Newton's laws) — exactly the setting where predicting ahead and respecting constraints pays off, versus a reactive controller that might only correct AFTER a constraint is already violated.

MPC's ability to explicitly weigh multiple simultaneous objectives (position, velocity, attitude, smoothness) via one cost function is also a natural fit for a landing task with several competing priorities.

BASICWhat is the prediction horizon here, and what does it represent physically?
Viva answer: Np=70 steps × dt=0.04s = 2.8 seconds of look-ahead; the MPC's predicted trajectory covers roughly the next 2.8 seconds of flight every time it's called.

This is fixed as a parameter, not adaptive; it was tuned to give the controller enough foresight for a smooth braking profile without an excessively large H matrix to solve.

INTERMEDIATEWhat is the control horizon, and how is it different from the prediction horizon?
Viva answer: Nc=12 is the number of DISTINCT future control moves the optimizer actually solves for; the prediction horizon Np=70 is how far ahead those moves' EFFECTS are predicted, with the control held constant at its 12th value for steps 13 through 70 (control-horizon blocking).

This keeps the optimization variable small (2×12=24 numbers) while still capturing a long-horizon trajectory, at some loss of optimality (the controller can't fine-tune control moves 13-70 individually).

BASICWhat is the cost function minimizing, in words?
Viva answer: A weighted sum of: (1) how far the predicted trajectory strays from the target state over the whole horizon, (2) how much control effort (absolute thrust/torque) is used, and (3) how abruptly the control changes from one move to the next.

Written as J = Σ(x−x_ref)'Q(x−x_ref) + ΣΔu'RΔu + Σ(ΔΔu)'S(ΔΔu), summed appropriately over the prediction/control horizons.

Viva answer: The controller tracks the target state more aggressively (accepting more control effort/less smoothness to reduce tracking error), since tracking error is now penalized more heavily relative to R and S.

If only one entry of Q is increased (e.g. the vy weight), only THAT state is prioritized more — this is exactly what the code does near the ground: a terminalFactor multiplies Q(1,1),Q(2,2),Q(5,5),Q(6,6) up by 1.8-3.5× below 35/15/8m altitude, sharpening focus on x, vx, theta, omega specifically as touchdown approaches.

INTERMEDIATEWhat happens if R is increased?
Viva answer: The controller becomes more conservative about control magnitude, potentially sacrificing tracking accuracy to avoid large thrust/torque commands — predicted trajectories become 'lazier'/gentler.

Since R is already small relative to Q by design (0.015/0.04 vs weights up to 260), a large increase in R could visibly slow the controller's response to disturbances.

INTERMEDIATEWhat is the receding-horizon principle, concretely, in this code?
Viva answer: Even though mpcController solves for a full Nc=12-move sequence (deltaU, 24 numbers) every call, only deltaU(1:2) (the very first move) is ever reconstructed into an absolute control and returned as 'control' — the rest of the optimized sequence is discarded and re-solved from scratch next tick.

This is what lets the controller correct for any mismatch between the linear model's prediction and the true nonlinear dynamics: it never blindly executes an old plan for more than one step.

ADVANCEDHow does MPC control the lander, end-to-end, in this code?
Viva answer: Every tick: (1) makeMPCTarget builds a target state from current altitude/distance-to-pad; (2) mpcController linearizes the dynamics at the current mass, discretizes, builds prediction+cost matrices, solves the QP via Gauss-Jordan, and returns the first optimized [T;tauRCS]; (3) applyTerminalLandingGuidance overrides that output entirely below 45m altitude with a separate PD law; (4) the resulting control is applied to the REAL nonlinear physics via simulateStep.

Notice the MPC's own predicted trajectory (built from a LINEAR approximation) is never itself executed open-loop — only its first command is applied, then the whole optimization re-runs against the true post-physics-step state, which is standard closed-loop MPC practice and also what corrects for linearization error.

Torque is bang-bang (full-scale or zero), not ramped like thrust — a deliberate asymmetry in the design (thrust ramps for smooth throttle feel, torque is instant since RCS thrusters are typically simple on/off jets in real spacecraft).

H · Numerical-methods questions

INTERMEDIATEWhy this timestep (0.04s)? What if it were larger?
Viva answer: 0.04s (25Hz) balances integration accuracy against real-time performance in a MATLAB timer callback; a much larger dt (e.g. 1s) would make Euler integration's O(dt) error large enough to visibly diverge from the true trajectory, could let the vehicle 'tunnel through' the landing-contact check between samples, and would make the MPC's Ad=I+A·dt discretization a poor approximation.

The project's own physics documentation explicitly reasons about this tradeoff, noting a single 0.04s step burns roughly 0.002% of the fuel mass, i.e. the zero-order-hold/constant-mass-during-a-step assumption is a negligible approximation at this dt specifically.

Code reference
physics/initializeLander.m; documentation/PHYSICS_ENGINE.md §4
BASICWhich integration method is used, and why?
Viva answer: Explicit (forward) Euler is the default (params.integrationMethod='Euler'); RK2 (midpoint method) is implemented and available as a drop-in alternative but not the shipped default.

Euler was chosen because dt=0.04s is small enough for its O(dt) local error to be acceptable, and it costs only ONE landerDynamics evaluation per step versus RK2's two — cheaper, which matters for staying inside the real-time control-loop budget.

Code reference
physics/simulateStep.m; physics/eulerStep.m, rk2Step.m
ADVANCEDWhat happens numerically if the timestep becomes very large, say 1 second?
Viva answer: Euler integration's local truncation error grows with dt (roughly O(dt²) per step, O(dt) accumulated over a fixed time span), so the simulated trajectory would visibly diverge from the true continuous dynamics; more critically, a fast-moving vehicle could 'jump over' the landing-pad contact test within a single 1-second step (moving many meters between samples), and the MPC's Ad=I+A·dt discretization — a first-order Taylor approximation of the true exponential ZOH solution — would become a poor model, likely destabilizing the closed loop.

tests/testPhysicsEngine.m's Test 9 specifically checks the OPPOSITE extreme (a very SMALL dt=1e-4) behaves sanely; the project does not include an automated test for a large/unstable dt, which is worth noting honestly if asked.

INTERMEDIATEWhat numerical solver does the MPC use, and why not MATLAB's backslash?
Viva answer: A hand-coded Gauss-Jordan elimination with partial pivoting (mpc/gaussJordanSolve.m), explicitly NOT MATLAB's \ operator or inv() — a deliberate project requirement (mapped to 'EEE 212 Experiment 5') to demonstrate the underlying linear-algebra method rather than call a black box.

It includes numerical safeguards beyond a textbook implementation: pivot selection scaled to the matrix's own Frobenius norm, ridge regularization for a near-zero pivot, and explicit singular/ill-conditioned flags returned to the caller for diagnostics.

ADVANCEDWhat is the difference between the two Gauss-Jordan implementations in this project?
Viva answer: mpc/gaussJordanSolve.m (used live, inside mpcController every 0.04s) adds ridge regularization and scale-relative tolerances specifically tuned for the MPC's cost-matrix H; numerical/gaussJordanElimination.m is a simpler, independently-tested version (fixed absolute tolerance 1e-12, no regularization) used by linearRegression/polynomialRegression and demonstrated standalone in testNumericalMethods.m.

Because g is read from params.g everywhere (never hard-coded elsewhere), changing it in initializeLander.m alone is enough to consistently re-parametrize the whole simulator (e.g. to Mars gravity 3.71 m/s²) without touching any other file.

EXAMINER TRAPWhy is Q's weight on vy/theta so much larger than on x/vx?
Viva answer: Because uncontrolled vertical descent rate or tilt are the two most SAFETY-CRITICAL states near touchdown (they directly determine whether the strict landing tolerances vyMax=0.60m/s and thetaMax=0.005rad are met), whereas horizontal position/velocity errors, while important, have a comparatively looser tolerance (vxMax=0.20m/s, pad halfWidth 7m) and more time/room to correct.

EXAMINER TRAPWhy does the controller need velocity, not just position?
Viva answer: Position alone tells you WHERE the vehicle is, but not whether it's approaching safely or about to overshoot/slam into the target; a vehicle could be exactly over the pad but descending at 20 m/s, which position error alone would never flag as dangerous. Velocity terms in the cost function (and the terminal guidance's explicit descent-rate schedule) are what actually prevent excessive approach speed.

This is also why the landing check itself tests vx/vy directly (not just position), and why the whole makeMPCTarget/applyTerminalLandingGuidance machinery is built around progressively-tightening VELOCITY targets by altitude, not just a single fixed position target.

EXAMINER TRAPWhy can't position alone be used to control the lander?
Viva answer: A pure position-tracking controller (effectively R,S huge, Q on velocity/attitude states set to zero) would try to correct position error as fast as possible without regard to how it gets there — it could easily demand a dangerously fast approach or an unstable oscillation between overshoot and correction, since nothing in the cost function penalizes excessive speed or attitude swings along the way.

The whole point of the 6-state formulation (not just [x,y]) is to let the cost function jointly shape the ENTIRE trajectory (how fast, how level, how smooth) not just its final destination.

EXAMINER TRAPWhy do you need attitude (theta) as a controlled variable at all?
Viva answer: Because in this model, attitude IS the only mechanism for producing horizontal thrust component — ax=(T/m)sinθ is zero whenever theta=0. Without controlling theta, no lateral maneuvering would be possible at all; and independently, theta must be driven to (near) zero before touchdown regardless of lateral needs, since the landing check requires |theta|≤0.005rad.

So theta serves two entangled purposes: an intermediate variable enabling lateral control, AND a terminal safety requirement in its own right — which is exactly why the terminal guidance law has to carefully SUPPRESS theta back toward zero even while still using it to brake lateral velocity, a genuine competing-objectives problem.

40Glossary

TermDefinition
ActuatorThe physical mechanism (engine, RCS thrusters) that produces a control input; actuator limits are hard, physical bounds.
Attitude safety boundaryThe hard clamp applied to theta (and the accompanying zeroing of omega) if it ever exceeds params.thetaMax=0.5236 rad after integration — a structural/gimbal-limit safety net, not a control law.
CallbackA function registered to run automatically in response to an event, e.g. a button press or a timer tick, rather than being called directly in a linear script.
Composite integration ruleApplying a basic quadrature rule (Trapezoidal, Simpson) repeatedly over small sub-intervals and summing, rather than over the whole interval at once, for better accuracy.
Control horizon (Nc)How many distinct future control moves are optimized before the control is held constant for the rest of the prediction horizon (12 here).
Control vector / control inputThe values a controller can actually command; here, [T;tauRCS], 2 numbers.
Cost functionThe quantity the MPC minimizes each call; here a weighted sum of tracking error, control effort, and control smoothness.
DiscretizationConverting a continuous-time model (differential equations) into a discrete-time model (difference equations) usable by a digital/step-based controller.
Euler integration (explicit/forward)The simplest numerical ODE integrator: x(k+1) = x(k) + dt·f(x(k),u(k)); O(dt) local error.
Finite differenceApproximating a derivative from discrete samples by dividing a difference of function values by a step size (forward, backward, or central).
Fuel-limited thrustThe exact, closed-form reduction of commanded thrust so that the fuel it would burn over one dt never exceeds the fuel remaining, computed BEFORE integration rather than clamped after.
Gain schedulingChanging a controller's gains (Kp, Kd, etc.) as a function of some measured quantity (here, altitude) rather than using one fixed gain for the whole flight.
Gauss-Jordan eliminationA method for solving a system of linear equations by row-reducing an augmented matrix to reduced row-echelon form; used here (with partial pivoting) as the MPC's direct QP solver instead of MATLAB's backslash.
Hard landingA touchdown that is detected (contactDetected) but fails at least one safety condition — classified as a crash even though it's not tumbling/out-of-bounds.
Ill-conditionedA matrix where small changes in input can cause disproportionately large changes in the solution; flagged here (not necessarily fatal) when the smallest pivot used falls below a warning threshold.
Lagrange interpolationConstructing the unique polynomial of lowest degree passing exactly through a given set of points, without solving a system of equations directly (uses Lagrange basis polynomials instead).
LinearizationApproximating a nonlinear system by its first-order (tangent-plane) behavior around a chosen operating point; here, hover (theta=0, T=mg).
MPC (Model Predictive Control)A control strategy that uses a model of the system to predict future behavior over a finite horizon, optimizes a cost function over that horizon, applies only the first optimized action, then repeats the whole process next step (receding horizon).
Operating point / equilibriumA specific state+control combination where the system is momentarily balanced; the hover point used here is theta=0, omega=0, T=mg, tauRCS=0.
Partial pivotingAt each elimination step, choosing the largest-magnitude available candidate as the pivot (rather than always using the diagonal entry) to improve numerical stability.
Prediction horizon (Np)How many future steps the MPC predicts ahead (70 here, i.e. 2.8 seconds at dt=0.04s).
Receding horizonThe principle that even though MPC plans Np steps ahead, only the FIRST planned control move is ever applied; the next tick, the whole prediction/optimization is redone from the new, actual state.
Receding-horizon control / stateless controllermpcController.m keeps no memory between calls (no persistent/global variables) — every call rebuilds the linear model and re-solves from scratch, using only the CURRENT state and target.
Regularization (ridge)Adding a small value to a matrix's diagonal to rescue a near-singular system from being unsolvable, at the cost of a small, controlled amount of bias.
Richardson extrapolationCombining two finite-difference estimates at different step sizes to cancel the leading error term and get a higher-order-accurate estimate.
RK2 (Runge-Kutta 2 / midpoint method)A more accurate integrator that evaluates the derivative at an estimated midpoint before stepping; roughly O(dt²) local error, at double the per-step compute cost of Euler.
Root-findingNumerically locating a value x where f(x)=0; four independent hand-coded methods (bisection, false position, Newton-Raphson, secant) are implemented and validated here as an auxiliary demonstration, NOT used inside the MPC.
Safe touchdownA touchdown that is simultaneous (all 3 feet), balanced (nearly level), inside the pad, and within all four kinematic tolerances (vx,vy,theta,omega) at once.
SaturationClamping a value to a physical limit, e.g. thrust to [0,Tmax].
Soft constraint vs hard constraintA hard constraint is guaranteed never violated by construction (e.g. actuator saturation is clamped in code); a soft constraint is only checked/penalized/corrected after the fact and may still be violated (e.g. the attitude safety check in applyMPCConstraints).
State vectorThe minimal set of numbers describing the system at an instant; here, [x;vx;y;vy;theta;omega], 6 numbers.
TelemetryThe time-series log of every state/control/derived quantity recorded once per simulation tick, used for the trail line, the labels, and post-flight analysis.
Terminal guidanceThe dedicated, non-MPC, altitude-scheduled PD control law (applyTerminalLandingGuidance) that takes over below 45m foot-altitude to guarantee a centered, upright, slow touchdown.
Timer (MATLAB timer object)An object that repeatedly fires a callback function at a fixed real-world rate (here, the FlightTimer drives timerCallback at Period=max(0.02,dt)≈25Hz).
Touchdown / contactThe geometric event where one or more of the three foot points reach the landing pad surface.
TumblingThe crash condition triggered when |theta| exceeds pi/2 (90°), i.e. the vehicle has rotated past horizontal.
uifigure / App Designer component modelMATLAB's modern UI framework; this project builds its interface by hand with the same component classes (uiaxes, uibutton, uipanel, etc.) that visual App Designer would generate.
Zero-order hold (ZOH)The assumption that a control input stays constant between two discrete update instants; used for both the physics integrator and the MPC's discretization.
